# 03｜决策引擎、跨模块联动与 AI 规范

## 1. 首要设计原则

**系统应决定“现在是否适合建议休息”，而不是决定“用户是否疲劳”。** 系统只具备有限活动信号、用户确认的任务和主动反馈，不得进行医学或心理诊断。

MVP 要在**无大模型、无网络、无健康打卡**时正常运行；AI 增强是可替换模块，不是应用单点故障。

## 2. 输入来源与可信度层次

| 来源 | 系统知道的事实 | 不允许推断 | 可信标记 |
|---|---|---|---|
| Windows 键鼠最近输入 | 最近有/无键鼠输入、持续活跃估计 | 是否在认真工作、是否眼疲劳、是否离开座位 | `observed_estimate` |
| 前台应用类别 | 某类别程序在前台 | 用户究竟在学什么、干什么、是否完成任务 | `observed_category` |
| 今日任务列表 | 用户已确认要做的任务、截止时间、完成状态 | 电脑活动自动证明完成任务 | `user_confirmed` |
| 模式开关 | 用户主动选择会议/专注/阅读/静默 | 真实是否在会议、是否真的专注 | `user_selected` |
| BodyLog 打卡 | 用户自己填报的当日感受 | 医学异常、疾病、准确疲劳指数 | `self_report` |
| 可选 LLM 输出 | 对文本或数据的建议性表达 | 可靠的事实来源或独立观察结果 | `model_suggestion` |

**用户确认 > AI 提议**：AI 不能覆盖用户输入和 Windows 原始采样解释；所有关联与总结均须标明来源。

## 3. 决策优先级（硬约束优先于优化）

### 3.1 状态门控（必须单测）

按以下顺序，任一满足即终止后续推荐：

1. **未授权 / 用户暂停**：`NONE`，采集与提醒均关闭。
2. **用户手动会议/静默模式**：`DEFER`，绝不弹出遮挡提醒；无连续追偿弹窗。
3. **系统锁屏/睡眠/活动信息未知**：`NONE` 或 `DEFER`（不能假装已确认休息）。
4. **近期已提醒或用户推迟未到期**：冷却结束前 `NONE`。
5. **达到候选休息窗口**（用户可配置，默认工作约 40 min；这是产品参数不是医学指导）：继续决策。
6. **短期临近已确认任务截止/课堂/会议**：优先非阻断延后，保留用户主动休息入口。不得无限延迟。
7. **自然间隙**：在前台应用切换或用户刚确认完成任务等信号附近，可以尝试柔性提醒；但“切换”不是任务结束证据。
8. **长时间没有适当间隙**：到设置的最长延迟（默认额外 20 min）时提供**始终可关闭的轻量提醒**，避免系统以“不打扰”为由永久不提醒。

### 3.2 推荐伪代码（M3 纯函数）

```python
def decide(ctx, cfg):
    if not ctx.monitored or ctx.manual_pause:
        return no_action('CONSENT_OR_PAUSE')
    if ctx.mode in {'meeting', 'quiet'}:
        return defer('USER_QUIET_MODE')
    if ctx.idle_seconds is None or ctx.observation_is_unknown:
        return no_action('OBSERVATION_UNKNOWN')
    if ctx.idle_seconds >= cfg.idle_threshold_seconds:
        return no_action('INPUT_IDLE_NOT_PROVEN_BREAK')
    if within_postpone_window(ctx) or within_cooldown(ctx):
        return no_action('COOLDOWN')
    if ctx.continuous_active_minutes < cfg.break_candidate_minutes:
        return no_action('BELOW_THRESHOLD')
    if confirmed_event_imminent(ctx, cfg) or ctx.mode == 'focus':
        return defer('SCHEDULE_OR_FOCUS_CONSTRAINT')
    if ctx.is_recent_switch or ctx.just_confirmed_task_done:
        return soft_notify('POSSIBLE_NATURAL_GAP')
    if ctx.continuous_active_minutes >= (
        cfg.break_candidate_minutes + cfg.max_soft_delay_minutes
    ):
        return soft_notify('SOFT_DELAY_LIMIT_REACHED')
    return defer('WAIT_FOR_OPPORTUNITY')
```

注：`observation_is_unknown` / `just_confirmed_task_done` 是需求语义，可根据 `PolicyContext` 扩充；日期跨天、长期静默、系统休眠需单测。`last_prompt_at` 更新要区分“已显示”与“仅决策”避免重复弹窗。

### 3.3 用户反馈是核心功能

提醒按钮：`BREAK_NOW`、`SNOOZE_10_MIN`、`SKIP`、`BAD_TIMING`；另可反馈“我正在阅读”。

- `BREAK_NOW` 仅表示用户**主动表示打算休息**，不是传感器证明。
- `BAD_TIMING` 要记录触发状态类别、策略原因、时间段（可粗粒度），为后续优化提供反馈。
- 用户连续跳过时，系统可**建议**调低频率，但不得无上限增加提醒或增加施压。
- 关闭监测后不得继续学习，也不发送后台网络请求。

## 4. 任务联动如何产生真实差异

1. **截止时间约束**：任务接近用户确认的截止时间时，不在关键输入中间发强打扰；提示可提前/延后但用户可覆盖。
2. **自然结束事件**：用户主动勾选任务“完成”，可视为一个可能的休息机会（比应用切换更强，但也不是健康证据）。
3. **手动情境**：用户点击“正在上课/会议/专注/阅读”，影响提醒策略；模式不会自动替用户删除任务。
4. **周期回顾**：比较自报“时机不合适”的提醒次数、任务完成数和类别使用时长，**不推断任务耗时**，除非用户自己开始/结束任务计时。
5. **任务时间冲突提示**：只针对明确时段的已确认任务做提醒；系统**不得自动挪动截止时间或睡眠时间**。

**不得做：** 因为前台 Chrome 就认定“娱乐”，因为用 VS Code 就认定“做完编程”；不得通过任务标题自行判断用户心理状态或健康情况。

## 5. 日报与周报：先事实、后叙述

### 5.1 FactSheet（只从数据库计算）

```json
{
  "period": {"type": "daily", "start": "2026-10-14", "end": "2026-10-14"},
  "data_quality": {
    "activity_monitoring_enabled": true,
    "covered_minutes_estimate": 180,
    "days_with_activity": 1,
    "wellness_opt_in": false,
    "missing_sections": ["wellness"]
  },
  "usage": {
    "active_minutes_estimate": 155,
    "by_category_minutes": {"CODE": 80, "BROWSER": 50, "OTHER": 25}
  },
  "tasks": {"confirmed_total": 3, "completed_by_user": 1, "open": 2},
  "reminders": {"shown": 3, "break_intent_confirmed": 1, "snoozed": 1, "skipped": 1, "bad_timing": 0},
  "wellness": null
}
```

上述 JSON **完全是虚构示例**，仅用于说明字段。`covered_minutes_estimate` 应计算受监测时段的实际覆盖，不应单纯通过活跃分钟相加来推算全天覆盖。

### 5.2 硬性文案规则

- **允许**：“今日监测到约 155 分钟活跃电脑操作（估计值）”“3 项任务中，有 1 项被你标记完成”“你曾点击 1 次‘开始休息’”。
- **禁止**：“你今天努力学习了 155 分钟”“你已经休息充分”“你的视力改善了”“完成 80% 工作”“你的情绪由焦虑转为开心”，除非有真实、合适且可验证的数据，且不得将关联冒充因果。
- **缺失**：“你未开启状态打卡，因此本报告不包含个人状态记录”；无活动授权时不得默认展示 0 分钟并说“今天没用电脑”。
- **对比**：周报必须标记“本周 N/7 天有可用数据”；至少 **3 个有效记录日**才生成趋势性表述，不足则只列事实和“资料不足”，不要猜测趋势。
- **建议**：采用低风险、可选择的习惯优化建议，例如“如果你觉得合适，可以调整提醒频率”。避免医疗诊断和对身体的负面评价。
- **来源可追溯**：报告标题旁可查看所采用的时间范围、监测授权状态、事实表和是否使用生成式 AI。

### 5.3 报告生成通道

1. `ReportFactsBuilder` 从 DB 汇总事实（可纯函数测试）。
2. `TemplateNarrator` 从事实表输出无幻觉报告，**P0 必须有**。
3. `OptionalLocalLLMNarrator` 为 M6 可选：用户主动启用并配置本地服务，对**经选择的事实表**生成自然语言；禁止由模型追加不存在的数字、因果推断或医疗结论；输出与事实表不一致则退回模板。
4. 不调用外部模型时，界面显示“规则/模板生成”，不能误称“AI 个性化医学报告”。

## 6. 可选本地 AI（M6，非比赛主链路依赖）

适配目标：本地 Ollama 等已由用户自主安装的推理服务；可在后续版本设计 LLM Provider 接口，默认关闭。使用 JSON 结构化输出，并在 UI 中展示模型建议、置信限制、用户确认。

**适合的 AI 任务**：
- 含糊清单的候选任务拆分和字段提议（不能凭空补充截止日期）。
- 将严格 FactSheet 改写成流畅、友好的日报/周报。
- 在有足够反馈样本时，辅助选择提醒策略的个性化参数（应有明确范围限制和规则兜底）。

**不适合的 AI 任务**：诊断疲劳、自动监控屏幕内容、读取未选择文件、估算没记录过的健康数值、自动应用封锁。

### 6.1 可选个性化学习的安全上限

先用确定性统计：根据最近至少 10 次**真实提示反馈**计算不同情境的“不合时宜”比率，再允许小步调整**软提醒偏好**（例如 5 分钟等级），不改变用户确认的最大推迟/静默规则；用户一键恢复默认。样本不足就不宣称模型学会习惯。

如果后期确实训练轻量分类器，应使用时间分割验证、真实基线对照、记录样本量和召回/误报，不应声称医疗级 AI。

## 7. 必须包含的策略场景测试

| 情境 | 预期 | 关键断言 |
|---|---|---|
| 监测未授权 | 不采集、不提示 | `CONSENT_OR_PAUSE` |
| 已授权、会议模式 | 延后，不弹窗 | `USER_QUIET_MODE` |
| 电脑长期无键鼠输入 | 不把它当作真实休息 | `INPUT_IDLE_NOT_PROVEN_BREAK` |
| 有任务但未确认 | 不参与截止时间决策 | 任务草稿不会进入 PolicyContext |
| 离截止时间 5 分钟 | 轻量延后 | `SCHEDULE_OR_FOCUS_CONSTRAINT` |
| 活跃过阈值且发生自然窗口 | 允许软提醒 | `POSSIBLE_NATURAL_GAP` |
| 没有自然窗口但延后到上限 | 允许不抢焦点软提醒 | `SOFT_DELAY_LIMIT_REACHED` |
| 用户点跳过后立刻采样 | 不再提示 | `COOLDOWN` |
| 监测关闭仍有待办任务 | 今日页可用 | 任务服务独立运行 |
| 无健康授权生成周报 | 正常输出、明确缺失 | `wellness: null` |
| 只有两天有效记录 | 无趋势结论 | 报告注明样本不足 |
| Windows 休眠 8 小时 | 不补作 8 小时活动 | 单调时间 / 间隔截断 |
